# Documentation Standards

Documentation is a product surface and a build artifact. It must be current,
specific, and mechanically checked.

## 1. Frontmatter

Every document under `docs/` except templates and the historical source brief:

```yaml
---
title: Human Readable Title
status: active
owner: architecture
last_verified: 2026-10-23
---
```

- `status`: `draft`, `active`, `planned`, `superseded`, `archived`.
- `owner`: a role, not a person, so ownership survives staffing changes.
- `last_verified`: the date the content was checked against reality.
- Update `last_verified` only when you actually verified the content.

## 2. When to update what

| Change | Update |
|---|---|
| New or changed API, event, IPC, error, or risk class | `docs/architecture/contracts.md` |
| New table, column, index, or retention rule | `docs/architecture/data-model.md` |
| Architecture or one-way-door decision | ADR plus `decision-log.md` |
| New capability status | `PROJECT_MANIFEST.json`, then regenerate |
| New command or path | `PROJECT_MANIFEST.json`, `README.md` |
| New tool or dependency | `tooling-inventory.md`, `THIRD_PARTY_NOTICES.md` |
| New failure mode | `debugging-playbook.md` or `troubleshooting.md` |
| New agent or model rule | `agent-roster.md`, `model-routing.md` |
| New test scenario | `test-plan.md` |
| Release | `release-verification.md` with evidence |

## 3. Structure

- Start with the purpose in one or two sentences.
- Put the most important rule first; do not bury it after background.
- Use tables for enumerations, checklists for gates, and short sections for
  procedures.
- Commands are copy-pasteable and state the working directory.
- Distinguish **planned**, **implemented**, **mocked**, and **blocked**.
- Link to the canonical document instead of duplicating it.
- Keep documents under ~250 lines; split by audience or task.

## 4. Diagrams

- Mermaid inside Markdown, fenced as `mermaid`.
- Use stable node names referenced by ADRs and tests.
- Prefer `flowchart`, `sequenceDiagram`, `stateDiagram-v2`, `erDiagram`.
- Label planned boundaries explicitly.
- Do not use a diagram to hide a missing decision; pair it with prose.

## 5. ADRs

Copy `docs/templates/adr.md`. Include context, decision, consequences, and
guardrails. An ADR is required for one-way doors: storage, security model,
orchestration split, desktop shell, licensing, and public contracts.

## 6. Runbooks

A runbook is written for someone under pressure:

1. Preconditions and permissions.
2. Exact commands.
3. Expected output.
4. Failure branches with recovery.
5. Stop conditions.
6. Evidence to capture.

Do not write “configure the thing” without naming the file, command, and value.

## 7. Generated documents

- `docs/agentcity/state-of-build.md` and `docs/repo-map.md` are generated by
  `scripts/generate-context.py`.
- Never hand-edit them; edit the manifest and regenerate.
- A commit that changes feature status must include the regenerated files.

## 8. Evidence

- Captured command output goes under `docs/agentcity/evidence/`.
- Use UTF-8 without BOM (see the debugging playbook).
- Never edit a result to make it pass.
- A screenshot is supplemental, not proof of behavior.

## 9. Validation

```powershell
python scripts/check-docs.py
```

The checker validates required docs, frontmatter, links, Mermaid fences, and
manifest consistency. It does not validate truth; reviewers do.

`scripts/generate-context.py` is not a check: it rewrites
`docs/agentcity/state-of-build.md` and `docs/repo-map.md` from the manifest.
Run it only when you intend to update those files, and commit the result.

## 10. Style

- Direct, specific, present tense.
- No marketing adjectives in technical docs.
- Define acronyms on first use in a document.
- Avoid “simply”, “just”, and “obviously”.
- Prefer “the app does X” over “we will maybe do X”.
- When something is unknown, say so and name the next check.
